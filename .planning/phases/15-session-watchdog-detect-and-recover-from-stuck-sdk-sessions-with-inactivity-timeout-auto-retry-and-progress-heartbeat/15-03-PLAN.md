<task id="15-03-01">
<title>Handle timed_out status in spec compliance</title>
<read_first>
- src/pipeline/spec-compliance.ts (runIncrementalComplianceLoop, how it handles step results)
- src/step-runner/types.ts (StepResult union with new StepResultTimedOut)
</read_first>
<action>
In `src/pipeline/spec-compliance.ts`, the `runStep` calls for gap fixes return `StepResult`. The code currently checks `result.status === "verified"` for success. The watchdog adds a new `"timed_out"` status.

Review all `runStep` calls in spec-compliance.ts:
1. `verifyRequirement` (line 128) — uses `verify: async () => true`, so it always gets "verified" or "failed". If timed_out, treat as gap (passed=false).
2. `verifyRequirementsBatch` (line 218) — same pattern. If timed_out, fall back to individual verification.
3. `runIncrementalComplianceLoop` gap fix (line 505) — if timed_out, treat as failed fix and defer the gap.

Add handling after each `runStep` call: if `result.status === "timed_out"`, log a warning and treat as failure/deferral:

```typescript
// After gap fix runStep in runIncrementalComplianceLoop:
if (result.status === "timed_out") {
  console.log(`[compliance] Gap fix for ${gap.id} timed out — deferring`);
  if (restorePoint) {
    try {
      execGitCommand(`git reset --hard ${restorePoint}`, ctx);
    } catch {
      console.warn(`[compliance] Warning: git reset failed for ${gap.id}`);
    }
  }
  deferredGaps.push(gap);
  continue;
}
```

For verification calls (verifyRequirement, verifyRequirementsBatch), check `result.status !== "verified"` to handle both "failed" and "timed_out" uniformly — these already have this pattern.
</action>
<acceptance_criteria>
- `src/pipeline/spec-compliance.ts` handles `"timed_out"` status in the gap fix loop
- Timed out gap fixes are deferred with git revert
- Console log contains `[compliance]` prefix for timeout messages
- `npx tsc --noEmit` exits 0
</acceptance_criteria>
</task>
